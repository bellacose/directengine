# Decisions

Settled choices. Agents follow these. Changing one needs Chris's approval and a new dated entry.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-11-15 | **Astro (static) + Supabase.** Edge Functions for server logic. One static deploy per site. | Static pages can't be overloaded by a crawl. One live directory lost its Google index when a recrawl of about 900 uncached pages overloaded its database. |
| D2 | 2026-11-15 | **Datasets hold facts; sites are config-only views.** A new directory is a file in `sites/`. | Chris wants many directories from the same data, with no code change per directory. |
| D3 | 2026-11-15 | **Each site renders its own page for a shop, in its own angle** (different facts per site). | Chris's choice. Each directory is complete on its own, and the pages differ. |
| D4 | 2026-11-15 | **Minimum verified facts per angle (default 3) before a site builds its own shop page.** | Prevents near-empty, near-duplicate pages across domains. |
| D5 | 2026-11-15 | **Pages are self-canonical.** No cross-domain canonical tags. | The pages differ by design (D3). |
| D6 | 2026-11-15 | **Facts are rows with a declared type**, not columns. | A new niche needs new fact definitions, not a schema change. |
| D7 | 2026-11-15 | **A fact is public only when a check was logged after its current value was set.** The log is append-only. | Verified facts are the product. Enforced in the database, not by habit. |
| D8 | 2026-11-15 | **Google Places is for discovery only. Store place IDs, nothing else.** | Google's Places policies allow storing only the place ID indefinitely, coordinates for 30 days, and other fields not at all. |
| D9 | 2026-11-15 | **Coordinates come from ZIP centroids** (GeoNames, CC BY 4.0, credited in the footer). | Meets D8. Good enough for sorting by distance and a directions link. |
| D10 | 2026-11-15 | **No ratings, reviews or generated text.** | Copied ratings in structured data risk penalties, and generated FAQs are the thin content that gets directories demoted. |
| D11 | 2026-11-15 | **Index gate of 5 listings per list page**, set per site in config. | Thin list pages hurt the whole site. |
| D12 | 2026-11-15 | **Affiliate approval, links and click tracking are per site.** Every click carries a site and page tag. | Networks approve each website separately, and Chris needs to see which directory earned what. |
| D13 | 2026-11-15 | **Featured (paid) placement is not built for launch.** | Shops won't pay before they see referrals. Add it once click data exists; it can be sold per site or as a bundle. |
| D14 | 2026-11-15 | **Verification calls are made by a person at launch.** No automated or AI voice calls to shops. | 20 to 40 calls is a day or two of work. Check the calling rules before automating calls to businesses that didn't ask for them. |
| D15 | 2026-11-15 | **`anon` has no database access.** Public forms go through Edge Functions. | One small, auditable surface for public writes. Rate limits live in the database. |
| D16 | 2026-11-15 | **The DOT physical site stays where it is for now.** | It's live on a different stack. Moving it onto this engine as a second dataset is a later decision, after this engine has a site in production. |
| D17 | 2026-11-15 | **First site is `dtf`, second is `laser`, metros are Tampa Bay and Buffalo.** | From the business-value ranking in the launch plan. Chris can change the order by editing `status` in the site files. |
| D18 | 2026-11-15 | **`pg` (node-postgres) for scripts that write to the database** (`sync-sites` first). Connects with `DATABASE_URL`, set only in the shell or host that runs the script. | Upserts that must not touch Chris's affiliate approvals need real SQL in one transaction, which the REST client can't do. Its query interface matches PGlite's, so the same code is tested on in-memory Postgres. |
| D19 | 2026-11-15 | **Scripts are TypeScript run directly by Node (type stripping, Node 22.18 or newer), no build step or `tsx`.** `erasableSyntaxOnly` in `tsconfig.json` keeps them to syntax Node can strip. | One less dependency; scripts import `packages/core` source as is. |
| D20 | 2026-11-15 | **Go on the 60-day test.** The DTF near-me terms clear the launch plan's 1,000-a-month cutoff. | Keyword Planner results in `docs/KEYWORDS.md` (H1). |
| D21 | 2026-11-15 | **`@supabase/supabase-js` for the build-time loader** (`apps/web/src/lib/load.ts`), with `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` as in ARCHITECTURE. Read-only, paged table reads; no embedded joins. | The build environment has the API URL and key, not a Postgres connection string. Tests run the real client against the migration on PGlite through a small PostgREST stand-in, so the queries are checked, not mocked away. |
| D22 | 2026-11-15 | **Admin app is React + Vite, talking to Supabase with `@supabase/supabase-js` as the signed-in user** (publishable key, email-link sign-in with `shouldCreateUser: false`). No router or UI library: hash routes and plain CSS. | ARCHITECTURE names React and Supabase Auth. Vite is the standard React build; supabase-js is Supabase's own client and handles the magic-link session. Every query runs under RLS, so the browser never needs more than the publishable key. |
| D23 | 2026-11-15 | **Admin data calls go through a small `Db` interface** (`apps/admin/src/lib/db.ts`): supabase-js in the app, SQL on PGlite in tests and in the local demo mode (`npm run dev:admin:demo`). `@electric-sql/pglite` is an admin dev dependency for that demo; production builds leave it out (tested). | Lets tests run the app's real queries against the real migration with RLS on, with no Supabase project; the demo gives screenshots and a try-out with fake data only. |
| D24 | 2026-11-15 | **`astro` 7 for `apps/web`, static output, no integrations or UI framework.** Built through `apps/web/run.ts`, which takes `--site <slug>` and `--fixture` and passes the rest to Astro. Sitemap and robots are plain endpoints, not `@astrojs/sitemap`. | D1 names Astro. Astro's own `--site` flag means a URL, hence the wrapper. The sitemap must come from `sitemapEntries()` with each page's own `lastmod` (rule 7), which a plain endpoint does directly. |
| D25 | 2026-11-15 | **`happy-dom` (dev only) to test the list-page filter script** on built HTML. The filter itself is a small `is:inline` script in the page, so no JavaScript file ships. | T4's acceptance needs the filters checked with JavaScript on. happy-dom is a test-time DOM, smaller than jsdom, and is never bundled into a page. |
| D26 | 2026-11-15 | **`/go/*` and `/track/` reach the Edge Functions through host routing the build writes** (`apps/web/src/lib/host-routing.ts`): a Netlify `_redirects` proxy, or a Cloudflare Pages `_worker.js` with `_routes.json`, each with the site slug baked in. Both are written until the build runs on one host. No new dependency. | The host isn't chosen yet (H2), and Cloudflare Pages can't proxy to another domain from `_redirects`. The slug in the route, not the page, tells the function which site earned the click. |
| D27 | 2026-11-15 | **Discovery uses Places API (New) over plain `fetch`, no Google SDK.** `scripts/discover` calls Text Search with field mask `places.id,nextPageToken` (ID-only SKU) using a server key `GOOGLE_PLACES_API_KEY`; the admin Candidates screen calls Place Details live with a separate browser key `VITE_GOOGLE_MAPS_BROWSER_KEY`, restricted to the admin's HTTP referrer and the Places API (New), and shows the result with "Google Maps" text attribution. | D8: the script never receives anything but IDs, so it can't store anything else. The review needs a name, address and website to recognise the shop, fetched each time and never saved. No new dependency. |
| D28 | 2026-11-15 | **Claim confirmation email goes through a `Mailer` interface** (`supabase/functions/_shared/mail.ts`) with a test double; **no provider chosen yet, Chris picks one.** Until then `mailerFromEnv` returns none and claims stay unconfirmed (approve with the override). Candidates, all with a plain HTTPS send API callable from an Edge Function with `fetch` (no SDK needed): **Resend** (Supabase's own docs use it; free tier 3,000 a month, 100 a day), **Postmark** (transactional-only, strong deliverability; free 100 a month, then paid), **Amazon SES** (cheapest at volume, more setup: domain verification, sandbox exit, request signing), **Brevo** or **Mailgun** (free tiers, broader marketing features we don't need). The key goes in Supabase function secrets as `EMAIL_API_KEY`, the sender as `EMAIL_FROM`; the sending domain needs SPF/DKIM set by Chris. | T19 needs email confirmation for claims; picking a vendor, its account and its DNS records is Chris's call. The interface keeps the choice to one function and lets tests check the whole flow without sending anything. No new dependency. |
| D29 | 2026-11-16 | **One typeface, Archivo (variable weight and width), self-hosted from `apps/web/public/fonts/`; no font package or font CDN.** Latin subset only (90 KB, preloaded), OFL 1.1 licence beside it; other characters fall back to the system font. List cards show a fixed set of fact slots per site (`angle.card`, else headline plus angle facts), each "Not checked yet" when unverified, so cards line up. | A file in `public/` is copied, not moved, so builds into another drive work on Windows (an npm font package made Astro move assets across drives and fail). No third-party request on page load. Fixed slots make missing data visible instead of reshaping each card. |
| D30 | 2026-11-16 | **Themes are Tailwind files in `sites/themes/<name>/`** (a v3 `tailwind.config.*` or a v4 `theme.css` with `@theme`), picked by `"theme"` in the site config; logos are files under `sites/` named by `brand.logo`. `apps/web/src/lib/theme.ts` reads a fixed set of semantic tokens (primary, accent, background, foreground, muted, border, input, fonts, radius) into the CSS variables `global.css` uses, and refuses colors it can't parse or that fail contrast. Tailwind itself is not a dependency and no utility classes are used. | Chris wants to theme a site by dropping in a Tailwind config, the format theme tools export. Reading only semantic tokens keeps every page's markup shared (rule 6) while the look changes per site. Config files are executed at build, so themes come from the repo only, never from uploads at runtime. |
| D31 | 2026-11-17 | **Site settings that change without a code change live in the database (`site_settings`), edited on the admin app's Site settings page:** the site name, the operator (name, email) and the theme (the Tailwind config and its CSS, stored as the text Chris pastes). A set field wins over `sites/<slug>.json` at build time; blank keeps the file's value. Structure (dataset, angle, metros, card slots, affiliates, index gates, status, domain) stays in the file. Theme configs, from the database or a theme folder, are read as data by a small parser in `@directory-engine/core` that accepts only plain values; Tailwind configs are never imported or run. Theme fonts come from `sites/themes/*/fonts/` (any theme's), so a saved theme can use any font file in the repo. | Chris wants to change a site's look and details from a backend without editing files. Storing executable config would let anyone with admin access run code in the build; storing text and parsing it as data removes that. Changes show on the next build (auto-rebuilds are a separate task). |
| D32 | 2026-11-25 | **Listings may come from licensed open place data and public records** (for example Overture Maps, Foursquare Open Source Places, state licence lists), after a licence check for each source recorded in its importer. Imported listings start as `draft` and keep their source. Google stays discovery-only (D8). | Building 1,000+ listings per niche by hand isn't realistic, and the factory plan (`docs/FACTORY_PLAN.md`) needs data at that scale. Licences that allow storage and commercial use keep the "hard-to-copy, allowed data" rule. |
| D33 | 2026-11-25 | **Agents may propose facts read from a business's own website, with the page URL as evidence; a fact goes public only when Chris approves it**, alone or in a batch, through `record_check()` (method `website`). A proposal is never a check, and nothing an agent proposes reaches `public_listing_facts` without that approval. | Only 25 of 92 DTF shops have the headline fact after hand checks. Reading sites is the slow part; approval stays human, so rule 1 holds. |
| D34 | 2026-11-25 | **Display ads are allowed, per site, off by default** (`ads` in the site config, T28). This amends D29's "no third-party request on page load" for sites that turn ads on. Ads need `ads.txt`, a consent banner where the network requires one, and an updated privacy page. No ads inside listing cards or facts. | Ads are the fastest way to break even while traffic grows; buyers (sponsors, featured spots, quote requests) follow once there's traffic to show. |
| D35 | 2026-11-25 | **The factory plan is the roadmap** (`docs/FACTORY_PLAN.md`): niches are chosen with the scorecard, one national site per niche, no near-copy sites (`tampa-makers` stays `planned`), no paid links, and the money order is affiliates, then ads, then sponsors and featured spots, then quote requests. | Chris approved the plan on 2026-11-25. It replaces the launch plan's money order in SPEC. |
